# 为什么现在要重新看智能体平台

## 从“做一个 AI 应用”走向“建设一个企业级智能体平台”

### 内容
- 过去两年，行业内主流智能体平台大多围绕知识库、流程编排、应用搭建展开
- 这些平台解决了“把大模型接进业务”的第一步问题，但还不完全等于企业真正需要的生产平台
- 对输电设计场景来说，我们更关心专业能力调用、老系统复用、面向业务人员、结果交付，而不只是问答，同时还希望减低定制智能体的门槛，工作流的配置方式对非技术人员有一定门槛
- 因此，我们需要一个能组织能力、连接系统、承载业务任务、使用门槛低的智能体平台

### 呈现形式
- 一页背景判断页
- 左侧写行业变化，右侧写输电业务诉求
- 中间用一句过渡语: 重点已经从“复杂配置”转向“连接 + 易用”

# 主流智能体平台的共性

## 知识库 + 流程编排，是当前最常见的产品形态

### 内容
- 第一类核心能力是知识库: 导入文档、切片、向量化、检索增强、问答引用
- 第二类核心能力是流程编排: 用可视化节点把提示词、模型、工具、判断、代码引入、输出串起来
- 在这个范式下，平台价值主要体现在“知识问答更准” + “流程自动化更方便”
- 这类能力非常重要，但更适合解决标准化、可预定义的任务

- 两栏对照图
- 左栏“知识库”，右栏“流程编排”
- 每栏下方列出 3 到 4 个典型能力点

# 传统平台的价值与不足

## 流程化思维很强，但任务化执行还不够强

### 内容
- 优点很明确: 结构清晰、可视化程度高、易于演示、适合标准流程落地
- 但它通常要求业务人员先想清楚流程，再把流程画出来
- 一旦任务存在探索性、迭代性、上下文依赖，纯流程方式就会变重
- 需要了解流程节点全要素的知识，复杂功能甚至需要一定的代码能力
- 对企业来说，一个能广泛使用的智能体平台，应当让业务人员能够用自然语言拆解任务，而不是先深度学习平台用法
- 这就要求平台不仅能编排流程，而且流程编排可以通过自然语言转换，甚至支持更灵活的助手式执行

### 呈现形式
- 左右对比
- 左边“传统平台优势”，右边“传统平台边界”
- 中间放一句判断: 无需学习也能定义任务

# 2026 年的新变量

## 以 OpenClaw 为代表，智能体平台开始出现新的产品范式

### 内容
- 新一代 AI 助手强调的，不再只是工作流，而是持续运行、任务执行、跨通道交互、能力扩展、技能封装
- 用户不一定先画流程，而是直接提出目标，由助手组织工具、技能和上下文去编制流程、封装技能，甚至直接完成任务
- 平台的重点从“静态编排器”转向“工具连接器”“自然语言翻译器”“自动编排器”“动态执行器”
- 这类范式对企业平台的启发非常大，尤其适合复杂、半结构化、跨系统任务

### 呈现形式
- 趋势页
- 标题下放一句大字: 从 Flow First，走向 Assistant First
- 下方列 5 个关键词: 能力扩展、自动编排、持续运行、任务执行、记忆上下文

# OpenClaw 给我们的启发

## 平台应该支持通过对话直接组织任务，而不是只依赖手工画流程

### 内容
- 第一，企业内部已有系统功能和算法能力在服务化后，应注册进平台，成为可调用能力
- 第二，很多任务可以加载 `Skill` 直接完成，不一定都要先拆成显式流程
- 第三，平台应允许助手按任务需要组合工具、服务、技能，而不是只沿固定链路执行
- 第四，用户提出目标后，平台应能辅助生成流程，而不是要求从空白画布开始

### 呈现形式
- 四象限启发图
- 每个象限放一个关键词: 服务与工具注册 / Skill 加载 / 动态组合 / 自动生成流程图

# Demo 总体结构

## 输电智能体平台应该从“知识与流程平台”升级为“对话工作台 + 能力中心 + 工作流”

### 内容
- 工作台负责承接用户任务，是统一交互入口
- 能力中心负责沉淀可复用能力，包括工具、服务、技能三大模块
- 工作流继续保留，承接稳定、标准、可复用的传统流程化任务
- 老系统、算法服务、专业程序，应统一服务化注册，供工作流和技能共同调用
- 这就是我们这套原型的基本判断

### 呈现形式
- 一张三层架构图
- 顶层“工作台”，中层“能力中心”，底层“企业服务与系统”
- 右侧单独挂出“工作流”

# 工作台是统一对话入口

## 所有任务都先从工作台进入，再按需要调用能力

### 内容
- 工作台不是单纯聊天框，而是用户发起任务的统一入口
- 用户可以在这里提出问题、下达任务、查看结果、继续追问
- 工作台向下可以调用工具、服务、技能，也可以触发工作流
- 对供应商来说，这意味着平台交互不应被拆散，而应统一在一个任务入口之下

### 呈现形式
- 一张主界面示意图
- 中间是会话区，左右可放“会话侧栏”和“配置抽屉”
- 下方用箭头连到工具、服务、技能、工作流

---

# 工作台不是聊天窗，而是任务调度台

## 从问答入口，升级为能力调用与任务执行入口

### 内容
- 用户在工作台里，不只是在问问题，而是在发起任务
- 平台需要根据任务目标，决定是直接回复、调用工具、调用服务、执行技能，还是进入工作流
- 同一个工作台，应支持不同模式切换，例如问答、搜索、执行、结果查看
- 这使工作台成为平台级入口，而不是某个单点应用页面

### 呈现形式
- 一条任务路径图
- 路径顺序: 用户目标 -> 工作台判断 -> 调用能力 -> 返回结果
- 每个阶段配一个简短说明

---

# 能力中心是平台的核心资产

## 平台能力应分层沉淀，而不是散落在单个应用里

### 内容
- 我们把能力中心拆成三类: 工具、服务、技能
- 工具偏通用原子能力，解决单一步骤问题
- 服务偏业务系统或专业算法能力，解决专业计算和专业处理问题
- 技能偏任务级能力，能够围绕目标自动组合多个步骤完成事情
- 这样拆分后，能力可复用、可注册、可治理、可被不同入口调用

### 呈现形式
- 三段式金字塔或三栏结构
- 每栏分别写工具、服务、技能的定义
- 下方补一句: 工作流也调用这些能力，但不是唯一入口

---

# 工具中心

## 沉淀通用能力，解决“单步可调用”问题

### 内容
- 工具是平台最基础的原子能力，强调标准输入输出、快速复用
- 工具举例: 搜索工具、指定站点搜索、网页爬取、法规规范检索、OCR 识别、坐标转换工具、GIS 地图读取、数据库查询等 8 个
- 工具既可以被工作流调用，也可以被技能动态调用
- 对供应商来说，工具中心需要支持统一注册、调用协议、权限控制、日志追踪

### 呈现形式
- 工具卡片墙
- 挑 8 个代表性工具做展示: 搜索工具、指定站点搜索、网页爬取、法规规范检索、OCR 识别、坐标转换工具、GIS 地图读取、数据库查询
- 右下角加一句: 工具解决的是“让智能体具备基础能力”

---

# 服务中心

## 把输电专业能力和企业已有能力接入平台

### 内容
- 服务不是普通小工具，而是更完整的专业能力单元
- 例如塔头规划、载流量计算、塔重估测、智能路径规划、路径方案比较、工程报告生成等，都更适合作为服务接入
- 服务的来源可以是算法程序、业务系统、计算引擎，也可以是已有平台接口
- 服务中心的目标，是把专业能力从“分散在系统里”变成“统一注册到平台上”

### 呈现形式
- 服务能力地图
- 左边写“专业算法服务”，右边写“业务系统服务”
- 中间列 6 个输电场景代表服务

---

# 技能中心

## 围绕任务目标组织能力，比流程更灵活

### 内容
- 技能面向的是任务，不是单个步骤
- 它可以围绕一个明确目标，自动组合工具、服务、知识、规则，完成较复杂任务
- 例如公共数据爬取、工程数据提取、路径方案比选、通用校审、初设说明书生成，都更适合作为技能沉淀
- 对用户来说，技能更接近“我想做什么”；对平台来说，技能是高复用的任务模板
- 这也是我们认为未来平台比传统流程更值得加强的方向

### 呈现形式
- 任务卡片式排版
- 每张卡片展示“技能名称 + 可完成的结果”
- 页脚一句话: 技能解决的是“完成一类任务”

---

# 工作流中心

## 工作流仍然重要，但定位回归到传统、稳定、可编排任务

### 内容
- 我们并不否定工作流，相反，它依然是平台的重要组成部分
- 只是它更适合稳定、规则明确、输入输出边界清晰的任务
- 例如路径方案比选流、报告校审流、协议资料生成流，都很适合做成显式工作流
- 在我们的判断里，工作流是能力调用的一种方式，不再是平台唯一中心
- 未来还可以支持通过对话辅助生成流程，再以 YAML 等形式导入导出

### 呈现形式
- 一张 Dify 的工作流示意图
- 节点可展示: 开始 -> LLM 分析 -> 工具/服务调用 -> 条件判断 -> 模板输出 -> 结束
- 下方或上方加一句: 工作流更像“可视化 SOP”

# 为什么企业老系统要服务化接入

## 不是推倒重来，而是把存量能力接进新平台

### 内容
- 企业内部已经有很多系统、程序、算法、脚本和数据库，真正有价值的是把它们接进来，而不是全部重做
- 这些能力可以通过 API、SDK、脚本封装、RPA 代理等方式服务化注册
- 一旦注册到平台，就既能被工作流调用，也能被技能和工作台调用
- 这会让平台成为“能力总线”，而不是另起炉灶的新孤岛

### 呈现形式
- 老系统接入示意图
- 左边放“既有系统 / 算法 / 程序”，右边放“平台服务中心”
- 中间用“封装注册”箭头连接

# 平台的建设需求

## 交付一套 2026 年的智能体平台 2.0

### 内容
- 第一，要交付统一工作台，承接任务入口、对话入口和结果入口
- 第二，要交付能力注册中心，至少支持工具、服务、技能三类能力管理
- 第三，要交付工作流能力，但不能把平台设计成只剩流程编排
- 第四，要支持企业系统接入、权限治理、调用审计、运行监控
- 第五，要支持通过对话生成流程、通过技能直接执行任务

# 总结

## 我们要的，不是另一个 Dify，而是一套面向输电业务的智能体平台

### 内容
- 我们认可主流平台的知识库与流程编排价值，但不希望平台停留在这一代形态
- 我们希望平台以工作台为入口，以能力中心为核心，以工作流为补充，以服务化接入为基础
- 平台的目标，不是展示 AI，而是把输电业务能力真正组织起来、调用起来、复用起来
- 这个 demo 的意义，就是把这个目标讲清楚，帮助供应商与我们对齐建设方向

### 呈现形式
- 收束页
- 结论: 从“知识库 + 流程”走向“工作台 + 能力中心 + 服务化智能体平台”

# 我们把数据中心解耦出来

## 知识库不从属于某一个智能体平台，而应成为企业级通用底座

### 内容
- 当前市面上的智能体平台通常自带知识库，但大多默认采用“上传文件后直接建库”的模式；对广东院来说，这种模式不够，因为院内已经有成熟的网盘、文件服务器和既有资料体系，新知识库必须支持直接接入，而不是要求重复上传
- 同时，广东院的知识文档类型多、格式杂、结构复杂，知识加工过程不能只靠默认参数，而需要支持预处理、切片、提取等环节的精细化策略定义
- 更重要的是，这套知识库不应绑定某一个平台，不只是服务未来的数智输电智能体平台，也应能服务当前使用的 Dify、部分部门使用的 RAGFlow，以及未来其他平台
- 因此，我们希望把数据中心从智能体平台里解耦出来，作为独立建设、统一供给、可跨平台复用的企业级能力底座

### 呈现形式
- 总结成解耦的三个原因 + 配图

# 文档中心

## 先把分散资料接进来，形成统一可管理的文档入口

### 内容
- 广东院的知识源头，不只是手工上传文件，还包括文件服务器、OSS 等既有资料来源
- 文档中心首先解决的，是多源资料的统一接入、统一管理和统一同步
- 它需要支持本地托管、对象存储、共享盘、文件服务器等多种接入方式，把已有资料体系纳入统一入口
- 文档进入文档中心后，不等于立即建库，而是先形成可追踪、可维护、可选择范围的资料池
- 这样，后续知识库构建时就不需要围绕某个平台重复导入，而是直接从统一文档底座中选取范围、建立知识库

### 呈现形式
- 文档来源汇聚图
- 左侧列出: 网盘 / 文件服务器 / 对象存储
- 中间为“文档中心”
- 右侧连接“策略中心”和“知识库”

# 策略中心

## 知识加工不能只靠默认参数，而要支持分阶段、精细化的处理策略

### 内容
- 广东院资料类型复杂，不同文档往往需要不同的处理方式，因此知识库建设不能只是“上传文件 -> 自动入库”
- 策略中心应至少包含三个模块: 预处理策略、切片策略、提取策略
- 预处理策略: 解决格式转换、结构清洗、页眉页脚清理、OCR 后整理、表头归一等问题
- 切片策略: 决定知识如何切开进入知识库，例如按标题切、按页切、按固定长度切、按表格行切
- 提取策略: 针对特定资料抽取字段、要点、实体关系等结构化信息
- 同时，策略中心还应支持参数配置、测试验证、预设保存，以及多策略组合与编排
- 这样一来，知识库构建过程就是可配置、可验证、可复用的，而不是一个黑盒流程

### 呈现形式
- 一张“三阶段策略链路图”
- 顺序可写: 原始文档 -> 预处理策略 -> 切片策略 -> 提取策略 -> 结果预览 / 保存预设
- 中间高亮: 策略定义 / 参数配置 / 测试验证 / 策略编排
- 页脚总结一句: 策略中心决定知识加工质量

# 知识库

## 把文档来源与处理策略绑定，形成可持续复用的企业知识资产

### 内容
- 知识库建成后，不应只服务某一个智能体平台，而应作为企业统一知识资产，对多个平台共同供给
- 这样可以避免在 Dify、RAGFlow、未来平台之间重复建库、重复同步、重复维护
- 对广东院来说，真正有价值的不是“每个平台都有自己的知识库”，而是“广东院有自己统一建设的知识库体系”

### 呈现形式
- 一张建库过程图，顺序可写: 选择文档范围 -> 选择处理策略 -> 加工建库 -> 形成统一知识库
- 右侧再补一组调用关系: Dify / RAGFlow / 数智输电智能体平台 / 未来平台，共同调用同一知识库
- 旁边补一句: 一次建设，多平台复用

# 数据中心与智能体平台的关系

## 数据中心负责知识供给，智能体平台负责任务交互与能力调用

### 内容
- 数据中心与智能体平台是协同关系，而不是包含关系
- 数据中心负责文档接入、策略处理、知识库建设和检索供给，沉淀企业统一的数据与知识资产
- 智能体平台负责工作台交互、能力编排、工具调用、任务执行和业务闭环
- 平台侧可以按需调用数据中心提供的知识库和检索服务，但不需要各自重复建设底层知识链路
- 这种分层方式，既有利于跨平台复用，也有利于后续替换智能体平台、升级模型能力和扩展知识处理方案

### 呈现形式
- 一张上下分层图
- 上层: 工作台 / 能力中心 / 工作流 / 智能体应用
- 下层: 文档中心 / 策略中心 / 知识库 / 检索服务
- 底部淡化补充: 存储 / Embedding / 向量库 / 文件源
